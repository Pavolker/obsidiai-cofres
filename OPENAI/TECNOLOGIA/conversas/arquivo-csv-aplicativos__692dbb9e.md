### 1. Usar a API do GitHub (caminho mais completo)

Se seus repositórios estão na sua conta (ou em uma organização), a API do GitHub permite listar tudo e ainda pegar metadados como:

- nome do repositório  
- descrição (que pode ser o “objetivo”)  
- linguagem principal  
- data de criação / atualização  
- se é público ou privado  
- URL, número de estrelas, etc.

Fluxo geral:

1. Criar um **Personal Access Token** no GitHub (Settings → Developer settings → Personal access tokens).  
2. Usar o endpoint da API, por exemplo (para um usuário):  
   - `GET https://api.github.com/users/SEU_USUARIO/repos?per_page=100`  
   ou, para uma organização:  
   - `GET https://api.github.com/orgs/NOME_ORG/repos?per_page=100`
3. Salvar o resultado em JSON e transformar em CSV com as colunas que você quiser (nome, objetivo, linguagem, data, etc.).

Se quiser, posso te fornecer um **script em Python** que:

- chama a API do GitHub  
- extrai: `name`, `description`, `language`, `html_url`, `created_at`, `updated_at`  
- grava tudo em um arquivo `repositorios.csv`.

---

### 2. Exportar via linha de comando (sem programar muito)

Se você usa terminal, pode usar `curl` + `jq` para converter rapidamente em CSV, por exemplo:

```bash
curl -H "Authorization: token SEU_TOKEN" \\
  "https://api.github.com/users/SEU_USUARIO/repos?per_page=100" \\
  | jq -r '.[] | [.name, .description, .language, .html_url] | @csv' \\
  > repositorios.csv
```

Depois é só abrir o `repositorios.csv` no Excel / Planilhas Google.

---

### 3. Listar manualmente via GitHub + planilha

É mais trabalhoso, mas possível se você tiver poucos projetos relevantes:

1. Na página “Repositories” do GitHub, filtra por owner (seu usuário ou org).  
2. Copia o nome e a descrição de cada repo para uma planilha.  
3. Define manualmente as colunas adicionais: objetivo, linguagem, status, tipo de app, etc.

Esse caminho é útil se você quiser uma classificação mais conceitual (objetivo do app, público-alvo, contexto de uso), que a API não “sabe”; aí você usa descrição + sua interpretação.

## Possíveis causas e hipóteses a investigar

Para diagnosticar melhor, convém considerar:

1. A chave de API pode não estar sendo realmente passada à requisição — por erro de ambiente ou configuração.  
2. A chave pode estar restrita a certas APIs ou não ter permissões adequadas.  
3. A chave pode ter sido gerada em um plano/conta que perdeu elegibilidade (free tier indisponível no país, ou exigência de billing) — a documentação aponta essa possibilidade. citeturn0search1turn0search0

## O que verificar primeiro (passos de debug)

Para entender se o problema está com a chave ou com a configuração, vale fazer:

- Verificar diretamente se a variável de ambiente com a chave está sendo lida corretamente no seu código (por exemplo, imprimir a chave — sem expor publicamente). Isso ajuda a confirmar se o problema é “chave = null / undefined”.  
- Conferir no console do Google Cloud / AI Studio se a chave está ativa, sem restrições de APIs, e se a API “Generative Language / Gemini” está autorizada.  
- Verificar se o modelo referenciado na requisição existe e está disponível na versão da API que você está chamando.  
- Testar com outra chave (gerada recentemente) para descartar que a chave atual esteja corrompida ou revogada.  
- Fazer uma chamada simples via `curl` ou script minimalista, fora de qualquer framework ou ambiente complexo — de modo a isolar variáveis de ambiente e configuração.
